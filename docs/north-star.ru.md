# North Star — JEV Benchmark

## Главный вопрос

> **Когда очень маленькая модель становится действительно полезным компонентом системы принятия решений?**

Проект исследует конкретную системную архитектуру:

> **Сколько полезной работы по принятию решений можно перенести в чрезвычайно маленькую модель, если дорогие части интеллекта — perception, planning, supervision и проверка ограничений — оставить за пределами runtime-модели?**

Это и есть North Star проекта.

Цель — **не доказать, что маленькие модели сами по себе лучше**, и не минимизировать число параметров ради минимизации.

Цель — найти границу, при которой tiny-модель становится достаточно полезной, чтобы её можно было использовать как часто вызываемый локальный компонент принятия решений.

## Почему это важно

Большая модель или серверная система может выполнять дорогую работу:

- perception;
- интерпретацию;
- planning;
- генерацию кандидатов;
- проверку ограничений;
- supervision;
- reward/judging;
- переобучение.

Устройство с ограниченными ресурсами не всегда может запускать такой интеллект на каждом решении.

Вместо этого внешняя система может свести задачу к компактному интерфейсу принятия решения:

```
дорогая система
      |
      | компактное состояние / legal candidates
      v
tiny runtime model
      |
      | решение
      v
детерминированный executor
      |
      v
наблюдаемый результат
```

Это относится к ESP32/STM32/RP2040-классу устройств, батарейным системам, робототехническим контроллерам, промышленной автоматике, IoT, wearable-устройствам и другим системам с ограничениями по latency или ресурсам.

## Что значит «полезна»

Tiny-модель полезна только в контексте всей системы.

Поэтому benchmark должен одновременно измерять четыре слоя:

1. **Качество решения**
   - accuracy;
   - reward;
   - regret;
   - survival / completion;
   - legal-action rate;
   - downstream utility.

2. **Runtime efficiency**
   - число параметров;
   - размер модели/артефакта;
   - memory requirements, если измеряются;
   - latency одного решения;
   - p95 latency.

3. **Selective reliability**
   - confidence;
   - abstention;
   - coverage;
   - частота fallback;
   - риск среди принятых решений.

4. **Системная полезность**
   - поведение в последовательной задаче;
   - robustness;
   - качество обучения;
   - количество вызовов дорогой модели;
   - cache hits;
   - trade-off latency/cost.

Benchmark должен отвечать:

> **Какова минимальная/дешёвая operating point, которая всё ещё даёт достаточно downstream utility для целевой системы?**

Универсального ответа нет, поэтому не должно быть и универсального победителя benchmark.

## Единица исследования

Единицей исследования является не:

```
model -> score
```

а:

```
декомпозиция системы
      |
      v
компактный decision interface
      |
      v
tiny model
      |
      v
runtime behavior
      |
      v
system utility
```

Результат интересен тогда, когда уменьшение runtime-компонента оставляет всю систему достаточно полезной.

## Гипотеза декомпозиции

Benchmark проверяет, можно ли перенести дорогой интеллект за runtime boundary, не разрушив полезное поведение системы.

### Candidate selection

```
perception / planner
        |
        v
legal candidates
        |
        v
tiny selector
        |
        v
executor
        |
        v
reward
```

Planner отвечает за генерацию допустимых кандидатов. Tiny-модель отвечает только за выбор среди них.

### Reward learning

```
environment transition
        |
        v
JEV / LLM judge
        |
        v
reward signal
        |
        v
RL learner
        |
        v
runtime policy
```

Здесь JEV — источник дорогого интеллекта на стадии обучения, а не runtime action selector.

## Логика развития benchmark

Задачи должны последовательно отвечать на всё более сложные версии одного системного вопроса:

| Этап | Вопрос |
|---|---|
| J01 | Может ли чрезвычайно маленькая policy вообще принимать решения и какова цена runtime? |
| J02 | Может ли tiny-модель извлекать полезное компактное состояние из реальных сенсорных данных? |
| J03 | Если дорогой planner уже сформировал legal candidates, может ли tiny-модель выбрать один? |
| J04 | Остаётся ли такой tiny selector полезным при последовательных решениях? |
| J05 | Может ли дорогая JEV-supervision дать learning signal, из которого получается полезное downstream behavior? |
| Future | Какие реальные edge/embedded задачи действительно сохраняют достаточную utility для deployment? |

J01 — измерительный baseline. J02 — compact perception. J03 — основная схема planner → tiny selector. J04 проверяет её в последовательной среде. J05 проверяет другую границу: дорогой интеллект во время обучения, дешёвое поведение во время runtime.

## Что необходимо сравнивать

Для серьёзной задачи benchmark должен включать как минимум:

- обычный/non-tiny baseline;
- несколько tiny capacities;
- вариант с внешней декомпозицией;
- fallback/escalation, если они применимы.

Нужно показывать trade-off, а не только лучший tiny model.

## Operating-point report

Результат должен позволять найти рабочие точки:

```
             downstream utility
                    ^
                    |
             A  *  |       larger model
                *  |
          B  *     |       tiny model
             *     |
       C  *       |
         +------------------------>
             latency / size / cost
```

Главный результат — **frontier и ограничения вокруг него**.

Для конкретного устройства должно быть возможно спросить:

- помещается ли модель в memory budget;
- достаточно ли мала latency одного решения;
- как часто требуется fallback;
- какая downstream utility сохраняется;
- что происходит при изменении representation;
- какую дорогую работу удалось вынести с устройства;
- сколько стоит эта внешняя работа во время обучения или эксплуатации.

## Что может опровергнуть идею

Научно полезным результатом будет и отрицательный результат.

Например:

- tiny-модель слишком часто требует fallback;
- при уменьшении модели теряется слишком много downstream utility;
- compact representation выбрасывает необходимую информацию;
- candidate generation делает задачу искусственно лёгкой;
- confidence недостаточно надёжен для selective execution;
- ошибки накапливаются в последовательной задаче;
- JEV выдаёт правдоподобный reward, но он не помогает обучению;
- стоимость внешнего supervision превышает выигрыш дешёвого runtime.

Это результаты исследования, а не провал benchmark.

## Критерий успеха North Star

Проект должен воспроизводимо показывать случаи, где:

1. дорогой интеллект вынесен из runtime decision loop;
2. оставшееся решение выполняется очень маленькой моделью;
3. система сохраняет полезное downstream behavior;
4. runtime-компонент даёт измеримое преимущество по ресурсам/latency;
5. confidence/fallback ограничивает цену ошибок;
6. результат выдерживает held-out, robustness и multi-seed проверки.

Одновременно benchmark должен явно показывать случаи, где эти условия не выполняются.

## Долгосрочная цель

Benchmark должен перейти от синтетических демонстраций к реальным decision workloads, сохраняя общий контракт:

```
дорогой интеллект
        ↓
compact decision interface
        ↓
tiny runtime component
        ↓
controlled execution
        ↓
измеримый system outcome
```

Конечная цель — построить карту того, **где tiny decision components действительно полезны**, а не leaderboard маленьких моделей.
